Stage 1
Load
Reads every supported file from data/raw/ into a Document object. Each format has a dedicated reader: PyMuPDF for PDF (page-by-page text extraction), python-docx for DOCX (paragraphs + table cells), openpyxl for XLSX (all sheets), stdlib csv for CSV, plain UTF-8 for TXT/MD/JSON. Database tables land here too as .txt files extracted by SQLAlchemy. A SHA-256 content hash is computed at load time. Load failures are flagged as LOAD_ERROR — the pipeline continues without crashing.
PyMuPDF python-docx openpyxl SQLAlchemy SHA-256 hash
loader.py
🧹
Stage 2
Normalise Text
Produces the clean_text field used by every downstream stage. Applies Unicode NFKC normalisation (e.g. ligatures, full-width chars → standard ASCII equivalents), strips control characters and URLs, collapses repeated whitespace. No information is lost — raw_text is preserved.
Unicode NFKC Whitespace collapse
text_utils.py
🌐
Stage 3
Language Detection
Uses langdetect (port of Google's language-detection library) which identifies language from character n-gram profiles — no word lists needed. Runs on the first 3,000 characters for speed. Returns a language code + confidence score (0–1). Documents with confidence < 0.8 are treated as unreliable. Only English (en) is accepted by default; all others are rejected with WRONG_LANGUAGE.
Character n-gram profiles langdetect min confidence: 0.80
✖ Off-language → WRONG_LANGUAGE rejection
language.py
🔁
Stage 4
Deduplication
Two-pass strategy. Pass 1 — Exact dedup: compares SHA-256 hashes computed in Stage 1. O(1) lookup, zero false positives.

Pass 2 — Near-duplicate detection (MinHash LSH): each document is represented as a MinHash signature using 128 random hash permutations over its word set. Signatures are indexed in an LSH (Locality-Sensitive Hashing) table — documents whose signatures agree on ≥ 85% of positions are flagged as near-duplicates. Scales to 100k+ documents in O(n) time.

Fallback: if datasketch is unavailable, uses Jaro-Winkler similarity (via rapidfuzz) on the first 2,000 characters.
SHA-256 exact dedup MinHash LSH · 128 perms Jaro-Winkler fallback threshold: 0.85
✖ Duplicate → DUPLICATE / NEAR_DUPLICATE rejection
dedup.py
📊
Stage 5
Quality Scoring
Heuristic gates — no ML, fully explainable. Four signals measured on clean_text:
  • token_count — document length in words (gate: 20 – 50,000)
  • avg_word_length — mean chars per word (gate: ≥ 3.0)
  • symbol_ratio — fraction of non-alphanumeric chars (gate: ≤ 0.30)
  • alpha_ratio — fraction of alphabetic chars (gate: ≥ 0.50)

Composite score = (token_score + alpha_score + symbol_penalty) / 3 where each sub-score is normalised to 0–1. Score shown in Report is diagnostic; the gates above are what actually reject documents.
token_count gate avg_word_length gate symbol_ratio gate alpha_ratio gate
✖ Any gate fails → LOW_QUALITY rejection
quality.py
🎯
Stage 6
Relevance Scoring
Seed-term coverage — domain-specific, no embeddings or training needed. Each seed term is tokenised into a word set. For each document the engine counts how many seed terms have all their tokens present in the document's token set.

score = hits / total_seed_terms

Current domain: carbonated beverages & packaging — seed terms include "carbonated", "beverage", "bottle", "PET", "sweetener", "carbon dioxide", "carbonation", "bottling", "syrup", "citric acid", etc. Documents below 2% coverage are rejected as off-domain.
Seed-term coverage Token set intersection min threshold: 0.02
✖ Below threshold → LOW_RELEVANCE rejection
contamination.py
✂️
Stage 7
Chunking
Splits each accepted document into overlapping token windows for retrieval. Window size: 150 tokens, stride: 130 tokens (20-token overlap between chunks). The overlap prevents a sentence being cut mid-thought at a chunk boundary. Chunks shorter than 10 tokens (tail fragments) are discarded.

Each chunk is the atomic unit of search & retrieval in Stage 10. A 6,000-token document produces ~44 chunks.
Sliding window chunk_size: 150 tokens overlap: 20 tokens
chunker.py
💾
Stage 8
Write Outputs
Accepted documents → data/curated/ as chunk files named {source}__{doc_id_prefix}.txt.
Rejected documents → data/rejected/rejection_manifest.json with each document's doc_id, source path, rejection reason, and exact detail string (e.g. token_count=4 < min=20). Every decision is fully auditable.
Curated chunks → data/curated/ Rejection manifest → data/rejected/
curator.py
🕸️
Stage 9
Build Knowledge Graph
Five sub-steps on accepted documents only:

1. Term extraction — unigrams (words > 2 chars, non-stopword, alphabetic) + bigrams (consecutive word pairs like carbon_dioxide, soft_drink) + Named Entity Recognition via spaCy en_core_web_sm (ORG, PRODUCT, GPE, LOC, PERSON).

2. Top-N selection — globally the top 25 most frequent terms become graph nodes.

3. Co-occurrence edges — two terms get an edge if they co-occur in the same document. Edge weight = number of documents they share. Edges below weight 2 are pruned.

4. PageRank (α = 0.85) — the same algorithm as Google's original search. Nodes co-occurring with many other important nodes rank higher. Drives node size in the visualisation.

5. Louvain community detection — maximises modularity (how densely connected a group is vs. random chance). Finds natural topic clusters. Drives node colour in the visualisation.
Unigrams + Bigrams spaCy NER Co-occurrence graph PageRank α=0.85 Louvain community detection NetworkX
graph_builder.py
📋
Stage 10
Report & Visualisation
Writes summary_report.json — total counts, rejection breakdown by reason, per-document quality and relevance scores, top graph nodes by PageRank.
Renders report.html — interactive bar/donut charts with per-document score table.
Renders graph_viz.html — interactive pyvis graph with community colours, PageRank-scaled node sizes, and hover tooltips showing term frequency & community ID.

Search (on-demand): TF-IDF vectorisation of curated chunks + cosine similarity ranking against a free-text query. Returns top-K chunks above a minimum score threshold. This is the GraphRAG retrieval layer ready to connect to any LLM.
TF-IDF Cosine similarity pyvis interactive graph HTML report
report.py · visualize_graph.py
